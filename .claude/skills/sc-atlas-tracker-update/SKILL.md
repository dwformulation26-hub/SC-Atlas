# SC Atlas Tracker Update

SC Atlas is a static dashboard tracking high-concentration subcutaneous (SC)
injection technologies. It's built so that adding a new finding never
requires touching the dashboard's code -- only two small database files.
This skill is that routine: edit the database, regenerate the derived data
file, push. Everything else about the app should stay untouched.

The daily research pipeline that *produces* findings lives in a separate
skill, `.claude/skills/sc-atlas-daily-scan/SKILL.md`. This skill is the
merge-and-publish half; that one calls into it.

## Why the split matters

The whole repo is deliberately built around one boundary: **content lives in
two plain-Python files, and the dashboard only ever reads a JSON file
generated from them.** Respecting that boundary is the entire point of this
skill -- it's what lets a routine update be a two-file diff instead of a
risky rewrite of working frontend code.

**Never edit these for a routine update** (this is the dashboard *application*,
not the data):
- `index.html`, `assets/app.js`, `assets/styles.css`, `assets/icon.svg`
- `scripts/build_data.py` -- the build logic itself. The one exception: if it
  prints a `WARNING` about a stage description it can't classify (see Step 3),
  that's a real signal the script needs a new rule -- but that's a deliberate,
  visible code change, not something to route around silently.
- `README.md`, `CHANGELOG.md`, `.gitignore`, `data/archive/*.xlsx` (old
  spreadsheets kept for provenance only, nothing reads them)

**These are what a routine update actually changes:**
- `data/technologies_db.py` -- the `TECHNOLOGIES` list. One dict per tracked
  technology.
- `data/deals_db.py` -- the `DEALS` list. One dict per deal/news finding.
- `data/dashboard_data.json` -- never hand-edited. Always regenerated by the
  build script, every run.
- `data/audit_log/<run-date>.json` -- the screening trail written by the daily
  scan skill.
- `data/internal_targets.json` -- the hand-maintained Hyperion / Thermicra /
  Dupixent benchmarks. This is data, but changes to it are rare -- only touch
  it if the user is specifically updating one of those three targets' own
  numbers, not as part of logging an external finding.

If you notice a change touching anything in the first list, stop and check
with the user before pushing -- it means the task in front of you isn't
actually a routine data update. In an unattended scheduled run there is no
user to ask: don't push it, and say so plainly in the run report.

## The update procedure

### 1. Find the working repo

**In a scheduled cloud routine** the repo is already checked out and
authenticated -- the routine declares `dwformulation26-hub/SC-Atlas` as its
git source, so the clone lands in the sandbox home directory (e.g.
`/home/user/SC-Atlas`) with a working `origin` and push credentials already
configured. Use the ordinary `Bash` tool. Do not build a token by hand, do
not clone over HTTPS with an embedded credential, and do not look for a
device bridge -- there isn't one in a cloud run.

```bash
cd ~/SC-Atlas && git status && git log --oneline -3
```

**In an interactive session on the user's own machine**, work in whatever
local clone they point you at, or clone one:

```bash
git clone https://github.com/dwformulation26-hub/SC-Atlas.git
```

### 2. Edit the database files

Use `sed -i` or a short Python read-modify-write script -- never retype a
whole file's contents from something you read earlier, since that risks
silently dropping or corrupting existing entries.

For a new technology, add a dict to `TECHNOLOGIES` in
`data/technologies_db.py`. Give it a unique `id` (lowercase,
underscore-separated -- this is what deals join against). Copy the shape of
an existing entry; the file's own docstring documents each field (`type` is
open-ended, `concentration_numeric` is `None` if undisclosed, etc).

For a new deal or news item, add a dict to `DEALS` in `data/deals_db.py`.
Its `technology_id` must match either a `TECHNOLOGIES` id or a
`deal_id_aliases` entry in `data/internal_targets.json`, and it needs a
unique `deal_id`. Set `flagged: True` if the sourcing is shaky or sources
conflict rather than silently picking one version -- that's what drives the
FLAGGED badge on the dashboard. Set `new_in_digest: True` if this is meant to
be highlighted as new since the last update, and set `new_in_digest: False`
on every previously-`True` row first, so only today's items surface in the
email.

### 3. Rebuild the derived data

From inside the repo folder:

```bash
python3 scripts/build_data.py
```

No dependencies -- stdlib only. Read what it prints. A clean run just reports
counts. A `WARNING` line means one of two things:
- A `stage_raw` string didn't match any bucketing rule -- either fix the raw
  text, or (if the phrasing is genuinely new) add a rule to `STAGE_RULES` in
  `scripts/build_data.py`, which is a legitimate, visible code change worth
  flagging to the user rather than hiding.
- A deal's `technology_id` doesn't resolve to anything known -- the finding
  will silently not appear anywhere on the dashboard if you let this pass.
  Fix the id rather than pushing anyway.

### 4. Verify before pushing

Don't trust "no warnings" as proof the edit landed correctly. Read back
`data/dashboard_data.json` (or grep for the new id/deal_id) and confirm the
fields you intended to set are actually there with the right values. This
catches typos in an `id` that would otherwise ship silently broken.

### 5. Commit and push

```bash
git add data/technologies_db.py data/deals_db.py data/dashboard_data.json
# add data/audit_log/<run-date>.json and data/internal_targets.json if touched
git commit -m "<describe what was added, e.g. 'Add Acme Corp SC platform + 2 deals'>"
git push
```

Before pushing, glance at `git diff --stat` (or the staged file list) and
confirm `index.html`, `assets/app.js`, `assets/styles.css`, and
`scripts/build_data.py` are *not* in it. If one of them is, that's the
"routine update" boundary being crossed -- pause and confirm with the user
this is intentional before pushing.

### 6. Report back

Tell the user plainly what was added or changed (technology names, deal
partners/dates) and confirm the push succeeded, ideally with the commit hash
or a link. GitHub Pages has a publish delay of a minute or two, so mention
that the live site may lag the commit.

## If git push fails on authentication

In a cloud routine, push credentials come from the routine's own git source
configuration. An auth failure there is not something to fix by generating a
token -- report it and stop; the fix is at the routine or GitHub App level.

On a local machine, git should already have a stored credential from
GitHub's OAuth device-login flow. If a push suddenly fails with an auth
error, the stored credential has likely expired or been revoked. See
`references/github-reauth.md` for how to walk the user through
re-authorizing -- a short flow where GitHub shows them a code they approve in
their browser, with no token handled by hand.

## If git operations behave strangely on a connected folder

This applies only to desktop/device-bridge sessions, not cloud runs. If
clone/commit/push show `unable to unlink ... Operation not permitted`
warnings, or a clone silently leaves the repo missing its `main` branch or
any remote-tracking branches (`git branch -a` shows almost nothing), this is
**not** git corruption -- it's the device folder's delete permission not
being granted yet. Git needs to delete its own temporary lock files during
normal operation, and a freshly-connected folder often doesn't allow
deletion by default. Request delete permission on the connected folder root
(this prompts the user for a one-time approval), then retry -- you may need
to `rm -rf` the half-broken clone and redo it once deletion is permitted.
Don't spend time debugging this as a git problem; it resolves the moment
deletion is allowed.
